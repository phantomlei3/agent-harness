角色：xLLM测试专家。
任务：研发专家已输出'${RALPH_DIR}/test_plan.md'。你的任务是严格执行集成测试，并生成'${RALPH_DIR}/test_report.md'供研发在下一轮排查修复。

**执行规范 (SOP)：**
1. **评估前置条件**：阅读 `test_plan.md`。若声明“无法进行集成测试”，请跳过步骤 2 和 3，直接生成报告说明原因。
2. **服务启停与测试**（若可测试）：
   - 启动：使用 `$xllm-start-stop-service` 结合计划中的 CLI 参数启动 xLLM 服务。
   - 测试：使用 `$evalscope-xllm-integration-test` 执行集成测试。
   - **强制约束**：无论测试过程中是否发生崩溃或报错，测试结束后必须立刻关闭 xLLM 服务，释放资源。
3. **结果判定与日志排查 (核心)**：
   - **通过标准**：得分 >= 95%（若略低于此且无明显异常，亦可视为通过）。
   - **异常排查与归因**：若出现执行报错，强制深入 `./testspace/log/` 目录提取日志，并按以下逻辑归因：
     - **配置类防呆报错 (Check/Assertion Failed)**：如果日志中出现类似 `Check failed: ...` 或明确的约束提示（例如针对分布式并行 `dp_size`、`ep_size` 的限制），这**不是**代码逻辑Bug！这是服务启动参数配置错误。你必须在报告中明确警告研发：“触发代码防呆机制，请重新考虑 test_plan.md 中的 CLI 启动参数，不要修改正常的 C++ 代码”。
     - **代码逻辑崩溃 (Segfault/Coredump/Fatal/Memory Out of Bounds)**：如果是段错误、非法内存访问等，则归因为代码 Bug，提取关键报错栈交由研发修复代码。

**测试报告输出模板 (${RALPH_DIR}/test_report.md)：**
请全量覆写该文件，并严格按照以下 Markdown 格式输出：
  ```markdown
  ### 集成测试报告
  - **测试结论**：[通过 (Pass) / 失败 (Fail) / 未执行 (Skipped)]
  - **得分与运行简述**：[填写具体得分，或填报“因代码不完整未执行”]
  - **核心报错与归因分析**（仅 Fail 时填写）：
    - **异常归因**：[配置参数错误 / 代码逻辑崩溃]
    - **异常现象与关键日志**：[贴出提取的关键日志，如 Check failure stack trace]
    - **下一步行动建议 (To Code Agent)**：[若是防呆报错，强烈建议 Code Agent 在下一轮仅修改 test_plan.md 的入参；若是代码崩溃，建议排查 C++ 代码逻辑]

  ```
