# Good and Bad xLLM Tests

Use these C++ patterns to distinguish durable behavior tests from tests coupled to xLLM internals. Adapt names and fixtures to the nearest existing test target.

## Good Tests

Prefer integration-style tests through a public seam. Keep the real domain objects that determine the behavior and replace only infrastructure boundaries when necessary.

```cpp
TEST(ChunkedPrefillSchedulerTest, SchedulesRequestsWithinTokenBudget) {
  auto engine = std::make_unique<FakeEngine>(/*num_blocks=*/512,
                                             /*block_size=*/32);
  auto scheduler = std::make_unique<ChunkedPrefillScheduler>(engine.get(), opt);

  for (auto& request : requests) {
    scheduler->add_request(request);
  }

  auto batch = scheduler->prepare_batch_test();

  ASSERT_EQ(batch.size(), 1);
  EXPECT_EQ(batch[0].size(), 3);
}
```

This test uses the scheduler seam and checks an observable scheduling result. It does not care which private queue or helper produced the batch.

Good tests:

- Exercise behavior through the public or established test interface.
- Describe what the scheduler, runtime, cache, layer, model, or service guarantees.
- Survive renaming, splitting, or replacing private helpers.
- Keep one logical behavior per test.
- Use small deterministic token ids, tensor shapes, configs, and prompts.

## Implementation-Coupled Tests

Do not verify internal call structure when the interaction itself is not the contract.

```cpp
// BAD: The test is coupled to one internal scheduling route.
TEST(ChunkedPrefillSchedulerTest, CallsAllocateBlocksOnce) {
  EXPECT_CALL(*mock_block_manager, allocate_blocks(testing::_)).Times(1);
  scheduler->add_request(request);
  scheduler->prepare_batch_test();
}
```

This test can fail after a harmless refactor even when the returned batch and KV block accounting remain correct. Assert those outcomes instead:

```cpp
// GOOD: The result is visible at the scheduler seam.
TEST(ChunkedPrefillSchedulerTest, AccountsForBlocksUsedByScheduledBatch) {
  auto total_blocks =
      util::max(engine->block_manager_pool()->num_free_blocks());

  scheduler->add_request(request);
  auto batch = scheduler->prepare_batch_test();

  ASSERT_EQ(batch.size(), 1);
  EXPECT_EQ(util::max(engine->block_manager_pool()->num_free_blocks()),
            total_blocks - 2);
}
```

## Side-Channel Verification

Verify through the same public contract that callers use. Do not bypass that interface merely because internal state is easier to inspect.

```cpp
// BAD: Reaches into a private queue to prove scheduling.
scheduler->add_request(request);
EXPECT_EQ(scheduler->waiting_queue_.size(), 1);

// GOOD: Observes the request in the prepared batch.
scheduler->add_request(request);
auto batch = scheduler->prepare_batch_test();
ASSERT_EQ(batch.size(), 1);
EXPECT_EQ(batch[0].front()->request_id(), request->request_id());
```

Use a narrow established test adapter such as `prepare_batch_test()` only when the repository already treats it as the seam. Do not add broad production accessors solely to expose private state.

## Tautological Tests

Do not calculate the expected value with the same rule as production.

```cpp
// BAD: Repeats the block calculation and can reproduce the same bug.
const auto expected_blocks =
    (request.num_tokens() + block_size - 1) / block_size;
EXPECT_EQ(required_blocks(request, block_size), expected_blocks);

// GOOD: Uses a worked example with an independently known result.
EXPECT_EQ(required_blocks(make_request_with_tokens(33), /*block_size=*/32), 2);
```

For kernels and device runtime behavior, an eager implementation or trusted CPU path can be the independent reference:

```cpp
auto eager_output = eager_model->forward(input, positions, kv_cache);
auto graph_output = graph_model->forward(input, positions, kv_cache);

test::verify_tensor_close(graph_output, eager_output);
```

Use this comparison only when the reference path is independent of the optimized behavior under test.

## Red Flags

- The test name says `calls`, `invokes`, or names a private helper instead of an outcome.
- A private refactor breaks the test while tokens, tensors, batches, cache state, and service responses are unchanged.
- The expected value is generated by copying the production formula.
- A fake returns a state that the real xLLM subsystem cannot produce.
- The test passes even if the regression is restored.
